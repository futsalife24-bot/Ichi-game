2026-10-10。UI004・UI005で初期プロフィール選択のマウス入力応答が約2.5秒でタイムアウトした。一方、両回とも選択結果は画面に反映され、UI005では通常プレイ・船・第二島・集合開始・再読込みまで成功した。入力失敗とセーブ破損を同一視しない。新UI IDは未受領で、この準備では画面を操作していない。

## コードと既存証拠から確認できたこと

`src/profile-ui.js` のプロフィールは通常のHTML `button`。初期選択では正規の `store.select` 後に選択画面を閉じ、`ensure()` の待機を解く。Enterはブラウザー標準のボタン操作であり、内部関数呼出し・イベント偽装・保存値注入ではない。通常操作が受け付けられたかは、選択後のＡの名前と星４・あそぶボタンを実画面で確認する。

`src/main.js:57` の待機解除後、保存の読込み、71行目以降の描画器、94行目の第一島、114行目の第二島などの初期化へ進む。初期化負荷が入力応答の遅れに関係する可能性はあるが、計測していないため原因は未確定。公式viewportをUI006で成功した844×390にする案は描画対象を減らす目的であり、改善を保証しない。ゲーム側の画質・タイマー・初期化順は変更しない。

保持タブは `1271483435`、接続先は `http://127.0.0.1:5207/`。UI005最終AXではＡ選択済み、星４、あそぶボタンのあるタイトル画面。Ａ・ＢはUI004で作成した同一の架空プロフィールを維持する。Ａのおやつ会開始はUI005で実操作した。再読込み後の星４は確認済みだが、集合段階が保持されたかは第二島の続き案内で次に確認する。完了扱いにしない。

## 診断表示の分離

専用サーバーはリポジトリの原本ファイルをそのまま読み、`index.html` の終端に診断スクリプト参照１個だけを追加する。`src`・音声・素材・CSS・SWは改変しない。診断スクリプトは画面に `details`、別タブへの通常リンク、観測記録を追加するだけ。書込みはゲーム保存とは別の `sessionStorage` の `harbor-review-visibility` キーだけで、`localStorage`、ゲーム変数、時計、表示状態、イベント発火へ介入しない。ログとDOM観測には負荷があるため、本体そのままの性能試験とは呼ばない。

非UI照合で、集合の見出しがゲーム初期化後に追加される可能性に対応するため、診断の見出し監視を文書配下の変更から該当見出しだけを選ぶ形に補正した。ゲーム本体の変更ではない。診断の記録追加で自分自身を再記録しない条件を設けた。新しいスクリプトは次の自然なゲーム再読込み時から有効となる。初期化後にスクリプトをブラウザーから注入しない。
